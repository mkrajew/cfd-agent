# ADR-0010: M3 is one run per benchmark on gpt-5.4, plus one or two generality tests

- **Status:** Accepted, 2026-11-27 (owner approval in chat; D1 of the M3 plan, `docs/superpowers/plans/2026-11-26-m3-fixes-and-gpt-5-4-campaign.md`). The scope of point 1, with `gpt-5.4` as the campaign model, was decided on 2026-11-26. On 2026-11-27 the owner approved the rest as proposed, and set the money limits of point 9 above those proposed.
- **Deciders:** the owner

## Context

Design 14.1 (accepted on 2026-10-28) planned the M3 campaign as a matrix in priority order: `gpt-oss-120b` with medium effort on all development benchmarks and the generality set with 5 repeats each; a Llama-3.3-70B comparison on a subset; and a reasoning-effort arm, about 65-75 runs. Design 12 says M3 is done when there are "statistics ready for the report".

M2 closed as a partial result on 2026-11-26. In its acceptance series (one frozen build, n = 3 per benchmark) `gpt-oss-120b` passed the Scorer in 3 of 15 runs, all on the lid-driven cavity at Re 100. In one comparison run, `gpt-5.4` produced a pipe solution that passed the Scorer when evaluated outside the pipeline, with the hand-written post-processing script, while the run itself stopped on its cost cap (one run, a different image). Hand-written, LLM-free solutions of all five development benchmarks pass the Scorer. The M0-M2 spend was $27.54 of the $35 envelope.

On 2026-11-25 the owner decided that M3 includes a commercial-model arm. On 2026-11-26 the owner decided the order of M3 (fixes first, then each of the five development benchmarks once on `gpt-5.4`, then further tests) and, later that day, narrowed M3: no further `gpt-oss-120b` campaign, no Llama-3.3-70B comparison and no reasoning-effort arm; the further tests are one or two generality tests on `gpt-5.4`. That is the whole campaign, and the owner said that it is enough (given in Polish; the repository records the English translation).

On 2026-11-27 the owner reviewed the M3 plan and answered (translated from Polish): "Raise the budget for one run to $10, raise the budget for the campaign to $50. Later my tasks also on the better model. I approve the rest, start." Asked whether the $50 covers only the model or all of M3, the owner chose the model alone; the question had stated that this means all of M3 up to about $60, with about $15 taken from the reserve.

## Decision

1. **Scope.** M3 has three parts: (a) the fixes chosen in the M3 plan; (b) one run of each of the five development benchmarks on `gpt-5.4`; (c) one or two generality tests on `gpt-5.4`, one run each. The generality task texts are written by the owner, and their reference data and a hand-written calibration are prepared first, under blind evaluation. This replaces the matrix of design 14.1. The money limits are in point 9.
2. **"Statistics ready for the report" means a table of observations.** One row per run, invalid runs included, built from the run records (status, failed stage, Scorer result and errors, Critic verdict, rounds and agreement, attempts, fix loops, tokens with the cached part, tracked cost, limits, wall time, served model, commit, image, validity), shown beside the M2 acceptance-series table. No success rates, no confidence intervals and no claim that compares the two models. The "benchmark success rate" headline of design 9.2 is not reported for M3.
3. **A frozen release is kept.** The tag `v0.3.0` before the first campaign run fixes `src/`, `docker/`, `pyproject.toml`, `uv.lock`, `scripts/`, the development benchmarks, the image, prompts, notes and the campaign configuration until the last campaign run ends. Only generality data, tests and documents may change. **The one exception** is the repair of a run that a defect of the pipeline's own code made invalid (point 5), under a new tag. The campaign configuration is final when the first campaign run starts (until then the owner may change the wall clock after a timing on the VM, and the change is recorded). The cost cap and budget are money limits that only the owner may change, and every change is recorded; the cap of point 9 is the command line's maximum, so it can only be lowered. Every run records its commit, image and prompt hashes. At this size the freeze matters for the generality tests: without it, it could not be shown that nothing learned from them reached the system (design 9.1). It costs nothing.
4. **`cfdagent bench` is not built in M3.** Six or seven runs are one sequence. A small tested script that runs them in order, records exit codes, does not start a run whose cap would take the total above the budget (the total can still end about one model call above it), stops after a broken run and refuses to run a task twice, together with a script that builds the table from run records, does the same job.
5. **Run rules.** No run is repeated to get a better result. A run is invalid only if it ended through a fault outside the agents' work: infrastructure (VM, disk, Docker, network, an Azure outage, HTTP 429 or 5xx that used up the retries), but not disk or memory exhaustion caused by the run's own output; or a defect of the pipeline's own code (an internal error, or a gate or tool that rejected or broke correct work) shown by a failing test; or a start with a configuration other than the approved one, which makes a run invalid whatever its result. A cost-cap or wall-clock stop, an agent failure, a failed score or physics the solvers cannot represent are results. The owner decides whether a run is invalid. An invalid development run is repeated once; if the cause is a code defect, after a fix under a new tag, without repeating earlier valid runs. A generality run is repeated only after an infrastructure fault or a wrong configuration, with unchanged code; no fix is made in M3 from what a generality run shows, and a session that makes any other fix does not read the generality files or their journal entries. Every run, invalid ones included, is reported with its cost.
6. **Generality preparation happens after the freeze,** in a session that changes nothing in the frozen set. The owner lifts and restores the deny rule on `benchmarks/generality/**` by hand. Nothing learned in this preparation changes the code (design 9.1). If a hand-written solution fails because of the frozen pipeline, the task is run anyway and the report says so; no task is replaced or dropped for a pipeline cause. A task may be replaced only for a defect of the task or of its reference that does not depend on the pipeline (ambiguous text, no verifiable reference, or physics or boundary types outside the stated solver limits, seen from the text before any solution is tried). The list and order of the tasks are fixed with the references, and the money for the whole list is checked, before the first generality run; every replaced, dropped or not-run task is reported with its reason.
7. **The campaign model is `gpt-5.4`**, a commercial hosted model, with medium reasoning effort. The open-weight evidence of the project is M1 and M2. `gpt-oss-120b` stays the default in the code.
8. **One new check of the Mesh gate** (a fix of the M3 plan, approved with its fix list, D4): the plan's run-time estimate, scaled to the real cell count, must stay within the run limit, and the Mesh agent is told the resulting cell ceiling.
9. **Money limits** (the owner, 2026-11-27): a per-run cost cap of $10 for `gpt-5.4`, the most the command line allows; a campaign budget of $50 of tracked model cost; and an M3 envelope, which covers the model, the VM, the fixed items and storage, of about $60 instead of $45. About $15 comes from the reserve, of which about $5 is left. The M3 plan's upper estimate, with the whole model budget spent, is about $62.7, above the envelope. The envelope is therefore checked before the generality runs, and anything above it needs the owner's approval.

## What follows from the narrower scope

- **One run per benchmark on `gpt-5.4` (n = 1) and three runs per benchmark on `gpt-oss-120b` from the M2 acceptance series (n = 3) are observations, not rates.** A pass means that the scored quantities of that run were within the thresholds; it shows no grid or domain independence. A failure shows one way the system can fail.
- The two sets do not compare the models: the builds, cost caps and wall-clock limits differ.
- One or two generality tests, one run each, cannot measure how general the system is. They remain the strongest evidence M3 has about unseen tasks, and the report must say how small it is. The agents can search the OpenFOAM tutorials, so each task is reported with its closest tutorial.
- Blind evaluation withholds the project's files only. The tasks are classic published cases, whose values a model may know from training, and no deterministic check shows that the reported quantities come from the solution. A reviewer therefore reads the post-processing script and the case set-up of every run that passes.
- Critic accuracy rests on at most seven M3 runs and on the four completed runs of the M2 acceptance series. The two are reported separately, because the Critic's model and the build differ.
- The effect of reasoning effort and a comparison with another open-weight model are not studied.
- A hosted commercial model can change on the service side; the served model name is recorded, and exact reproduction is not guaranteed.

## Alternatives considered

- **Keep the design 14.1 matrix on `gpt-oss-120b`.** Rejected by the owner.
- **Several repeats on `gpt-5.4`.** Not chosen. At about $3 per run (a guess from one run), five repeats of five benchmarks would cost about $75, above the envelope.
- **No freeze at this size.** Rejected: see point 3.
- **Build `cfdagent bench`.** Rejected: no scientific gain at this size; it would cost implementation and review.
- **Repeat each failed run once.** Rejected: it would turn n = 1 into the better of two tries.
- **Replace or repair a generality task that the frozen pipeline cannot handle.** Rejected: it would select or tune the test set to the system's abilities.
